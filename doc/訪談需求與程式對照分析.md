# 訪談需求與程式對照分析

**分析對象**
- 需求來源：`doc/訪談紀錄`
- 客戶端：`client.html`（下單改類申請）
- 後台端：`cms-現買改資買.html`（現買改資買 CMS 原型）

**結論摘要**  
兩支前端皆為 **Demo／原型**，已覆蓋「現股→融資申請、部分張數、額度／券源提示、後台查詢審核」等主路徑，但對照訪談中的 **時間鎖定、事前可過／不可過判定、維持率補繳、券配額即時控管、人工改帳後限制說明、結算串接與電話／線上並行規則** 等多項關鍵需求與限制，**尚未滿足或僅以假資料／隨機模擬呈現**。下列依優先級列出缺口與建議。

---

## 1. 訪談需求梳理（與線上化相關）

### 1.1 客戶端／線上申請

| 需求／限制 | 訪談重點 |
|---|---|
| 事前告知可過／不可過 | 申請前即時明確告知，避免等完才失敗、影響交割 |
| 時間鎖定 | 約 **15:00** 前完成；逾時不接受；需保留彈性但不可隨意改 |
| 指定張數（分單） | 可改部分張數；**價格不可動**；類別含現股／融資／融券 |
| 額度不足 | 需提示本筆所需金額；可對照可用融資／剩餘額度 |
| 配額（券）不足 | 核心限制之一；線上需自動判斷；要不到券則放棄改類 |
| 維持率不足／補繳 | 線上申請補繳：先入金再送申請，再通知後台 |
| 人工改帳後限制 | 曾人工改帳過，APP **無法再自動調整**；需讓客戶清楚知道 |
| 完成後通知 | 改帳完成後系統通知客戶自行查看，不自動輸入 |
| 風險控管 | 邏輯必須嚴謹攔截；結算不接電話救火；需減輕人工判斷負擔 |

### 1.2 後台／作業端

| 需求／限制 | 訪談重點 |
|---|---|
| 審核流程 | 考慮自動化審核，或由客服／後台審核改帳單 |
| 複查 | 改完建議人工再檢查一次 |
| 紀錄產出 | 總改類單 **SERD1A**；後續 **SEP32** 轉檔、**C31** 送交易所；證金／集保傳送 |
| 額度／券即時 | 即時掌握已用／剩餘券量；自動算補繳、利息並通知後台 |
| 電話＋線上並行 | 需預先定義同時進線時的處理規則 |
| 結算串接 | 與元大證券、交易所邏輯一致，避免帳目無法軋平 |

> 說明：SPP01／SPP02、SV102、已補單移出等屬既有 AS400 作業流程，Demo 可不直接重現，但線上化後台應能銜接其結果狀態或改類送出。

## 3. 問題與未滿足需求（含建議）

優先級：**P0** 上線風險／訪談硬限制 · **P1** 核心體驗與作業完整性 · **P2** 體驗強化／後續串接

---

### P0-1｜申請前「可過／不可過」未真正攔截

**訪談**  
客戶申請前必須即時明確告知能否通過，避免等待後才失敗。

**現況**
- 頁尾可顯示「申請後剩餘額度」為負數（`remain < 0`），但 **仍可按下一步並送出**。
- 券源不足以 `Math.random()`／URL 參數模擬，且發生在 **送出之後**，不是送出前預檢。
- 進場 `credit`／`quota` 以隨機 Notice 演示，非依真實資格／額度計算。

**建議**
1. 送出前強制規則引擎：信用資格、剩餘額度、券配額、維持率、是否曾人工改帳、是否逾時。
2. 不可過時：**禁用送出**，並顯示明確原因與下一步（提高額度／補繳／放棄／改張數）。
3. 可過時於確認頁顯示「預檢通過」與本筆所需金額／佔用券量。

---

### P0-2｜15:00 時間鎖定未實作

**訪談**  
三點前須完成；三點後不接受改帳，否則無法結帳。時間應鎖定，但保留彈性。

**現況**
- 僅有空狀態文案「超過可改類時間」。
- **無系統時間判斷**；需手動 `?view=empty` 才看得到空頁。
- CMS 無截止時間提示、逾時單攔截或彈性開窗機制。

**建議**
1. Client：以伺服器時間判斷截止；逾時自動切空頁並關閉申請入口。
2. CMS：顯示今日截止倒數；逾時單不可「通過／送出改類」（需主管彈性覆寫時另開權限與稽核 log）。
3. 產品規格寫明：客戶截止時間 vs 後台作業緩衝時間是否相同。

---

### P0-3｜券（配額）即時控管不足

**訪談**  
核心限制為額度不足與配額不足；線上需自動處理；需即時掌握當日已用／剩餘券量。

**現況**
- Client：券源不足為 Demo 隨機結果。
- CMS：無券源庫存、無佔用／釋放、無「配額不足」駁回類型的作業輔助資訊。

**建議**
1. 後端維護標的日券庫存；申請預扣、駁回／失敗釋放。
2. Client 申請頁即時顯示「本檔可改券量／預計佔用」。
3. CMS 審核／送出時顯示券餘額；不足則不可通過或自動駁回並同步客戶狀態。
4. 「打電話向結算要券」改為系統工單／自動要券流程；要不到則明確失敗。

---

### P0-4｜維持率不足與線上補繳流程缺失

**訪談**  
維持率不足可走線上補繳：先入金 → 再送申請 → 通知後台；並需自動計算補繳金額、利息。

**現況**  
兩支 HTML **皆無** 維持率檢查、補繳金額／利息試算、入金確認、補繳申請狀態。

**建議**
1. 預檢失敗類型新增「維持率不足」。
2. 導流：試算應補金額／利息 → 入金指引 → 入金確認後才可送改類。
3. CMS 顯示「待補繳／已入金待審／可改類」狀態，並通知後台。

---

### P0-5｜曾人工改帳後「APP 無法再自動調整」未告知／未攔截

**訪談**  
人工改帳過一次後，即使已簽同意書，APP 也不會再自動調整；客戶常不知情，只能再致電人工。

**現況**  
無「曾人工改帳」旗標、無說明文案、無進線導流規則。

**建議**
1. 後端標記 `manualReclassOnce`（或同等帳務事件）。
2. Client：進場或送出前明確警示；必要時改為「僅能客服人工處理」並鎖線上申請。
3. 申請紀錄區提供此限制的說明 FAQ／狀態。

---

### P0-6｜CMS 審核明細／通過駁回入口無法操作（實作缺陷）

**現況**
- 已實作 `DetailModal`（含通過／駁回），且有 `detailRow` state。
- 表格列 **沒有任何 `setDetailRow(...)` 呼叫**，明細彈窗實際上 **打不開**，審核按鈕無法使用。

**建議**
1. 列點擊或「明細」按鈕呼叫 `setDetailRow(r)`。
2. 待審核列提供列上快捷「通過／駁回」。
3. 明確區分流程：「審核通過」vs「送出改類（轉檔／送交易所）」兩段狀態，避免混淆。

---

### P0-7｜「送出改類」未更新單據狀態／未對接轉檔語意

**訪談**  
改帳完成後需有紀錄（SERD1A），再 SEP32、C31；融資送證金、現股送集保。

**現況**
- `confirmSubmit` 只提示「已送出改類 N 筆」，**不更新** `status`，也不區分審核通過與轉檔送出。
- 匯出 CSV 可當清單，但非 SERD1A／轉檔作業介面。

**建議（Demo 階段即可先做狀態機）**
1. `pending` → `approved`（審核）→ `submitted`／`exported`（送出改類）→ `settled`（結算回寫）。
2. 送出改類僅允許已通過且未送出之單。
3. 後續再接 SEP32／C31／證金／集保 API 或批次；UI 顯示傳送結果與失敗重送。

## 4. P1 缺口

### P1-1｜改類方向僅支援現股→融資

**訪談**  
改成交方式涵蓋現股／融資／融券；使用者可指定類別與張數。

**現況**
- Client 文案寫死「僅支援現股買進 → 融資買進」。
- CMS 雖有 `short` 選項與 Tag，Mock 幾乎全是 `cash → margin`；無後台改類別／改張數操作。

**建議**
1. 若 MVP 只做現買改資買：在規格與 UI 明確標示範圍，並與訪談對齊「融券／其他方向為 Phase 2」。
2. 若需對齊訪談：Client 增加目標類別選擇；CMS 支援審核時檢視／調整目標類別與張數（價格仍不可改）。

---

### P1-2｜額度不足提示未達「本筆所需金額」完整度

**訪談**  
額度不足會跳出本筆所需金額；可至基本資料看可用融資金／剩餘額度。

**現況**
- Client 有預估融資與剩餘額度，但超額仍可送出。
- 額度不足 Notice 文案偏「融資餘額／去申請額度」，與「本筆需要 X 元、尚缺 Y 元」不完全一致。
- CMS 審核畫面無客戶可用額度／本筆需求對照。

**建議**
1. Client 阻擋超額並顯示：所需、可用、不足。
2. CMS 明細加「客戶信用額度／可用／本筆預估」供審核複查。

---

### P1-3｜客戶完成後通知與申請狀態語意不完整

**訪談**  
改帳完成後系統通知客戶自行查看。

**現況**
- Client 送出後多數直接標成「已通過」（略過待審）。
- 無推播／站內通知原型；狀態缺少「審核中／已駁回／處理中」。

**建議**
1. 送出後預設「審核中／處理中」，CMS 通過後再變「已通過」。
2. 狀態對照推播文案；駁回需帶回原因（對齊 CMS `reason`）。

---

### P1-4｜電話與線上同時進線規則未設計

**訪談**  
需事先規劃電話與線上同時進線的處理規則。

**現況**  
兩支程式皆無鎖定、併單、客服接管、重複申請防呆。

**建議**
1. 同一委託／標的申請中鎖定；客服進線可「接管」並作廢線上單或合併。
2. CMS 顯示「線上申請中／客服處理中」來源與操作者。
3. 產品寫清：先到先審、客服優先、或券源預扣優先等規則。

---

### P1-5｜複雜交易組合（紙單、紙券抵繳、現償等）未處理

**訪談**  
多種交易方式組合需能辨別；邏輯漏洞會導致與結算／交易所無法軋平。

**現況**  
Demo 僅簡單現買列；無組合情境與攔截。

**建議**  
建立不合格組合規則表（與結算共同簽核）；預檢直接拒絕並給客服話術／原因碼。

---

### P1-6｜Client ↔ CMS 資料未串通

**現況**  
Client 用 `localStorage`；CMS 用 `MOCK_ROWS`；互不影響。

**建議**  
Demo 可用同一 Mock API／JSON；正式需同一申請單 ID、狀態雙向同步。

## 5. P2 及其他觀察

| 項目 | 說明 | 建議 |
|---|---|---|
| 價格不可更動 | Client 已符合 | 維持；CMS 若開放改張數也勿開放改價 |
| 空頁客服電話 | 已有 `0809-089-001` | 與真實服務時間文案對齊 |
| CMS 匯出 | 可當改類名單紀錄雛形 | 欄位對齊 SERD1A；必要時加「改類張數」欄（目前多為成交張數） |
| 改類張數 vs 成交張數 | 訪談強調可只改部分張；CMS 僅 `lots` | 增加 `convertLots`／剩餘現股張數 |
| 隨機 Demo 行為 | `notice`／`source` 隨機不利驗收 | Demo 改為明確 query 開關，預設可預期路徑 |
| 結算串接 | 訪談要求與元大／交易所一致 | 屬後端；前端預留狀態與錯誤碼即可 |
| SPP／補單作業 | 屬既有後台 | 線上化可不重做 UI，但狀態需能對應「可改／不可改」 |

## 7. 建議實作順序（給下一版 Demo）

1. **修 CMS 明細入口**，打通審核通過／駁回；釐清「審核」與「送出改類」狀態。  
2. **Client 預檢硬攔截**：逾時、額度、券源、信用資格、曾人工改帳。  
3. **補「可過／不可過」與所需金額文案**，避免送出後才失敗。  
4. **券配額與維持率／補繳** 最小可行流程（可先用假 API）。  
5. **Client／CMS 共用申請單狀態**；送出後為審核中，通過後再通知。  
6. 與結算／作業確認：截止時間彈性、SERD1A 欄位、電話併線規則，再擴充融券與複雜組合。

## 8. 附註
